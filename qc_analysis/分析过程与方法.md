# UE 无 BSR/SR 问题 — 日志分析过程与方法

问题：UE 在 13:28:13–13:28:35（服务小区 PCI-347 / N78）期间虽有有效 RRC 配置，
PDCP 缓冲持续累积约 20 秒，但未发送 BSR/SR，也没有 RACH 去请求上行授权。本文记录完整分析过程。

## 0. 输入文件

| 文件 | 大小 | 内容 |
|---|---|---|
| ITR-8 mobility test sender1.hdf | 1.9 GB | QXDM 原始 modem 日志（含全部消息） |
| log.txt | 383 MB | QXDM 文本导出，只覆盖设备时间 07:52:26–07:58:44，共 636,124 条 |
| tcpdump-mo.pcap | 8.2 MB | UE→服务器方向的抓包（IPv6/UDP/RTP） |
| tcpdump-mt.pcap | 4.7 MB | 另一方向的抓包 |

## 1. 第一眼检查 log.txt（发现它没有解码字段）

先用 ripgrep 看头几行和消息类型分布：

```
[0xB8C9] LOG 07:52:26.198640 NR5G LL1 FW RX Control AGC Length: 5152 1 0x980100...（原始hex） 0 Qualcomm ...
```

结论：log.txt 是 QXDM 的 **raw 文本导出**，只有消息名 + 原始 hex，没有任何解码后的字段。
想读 BSR 内容、Drop Reason、RLM Purpose 等字段，必须用带解码数据库的工具处理 HDF。

用 `rg -o '... LOG <time> <消息名>'` 统计出 log.txt 含 45 种 NR5G 消息，
其中与本次问题相关的有：

```
0xB873 NR5G L2 UL BSR          0xB889 NR5G MAC RACH Trigger
0xB88A NR5G MAC RACH Attempt   0xB8AE NR5G MAC Skip UL TX
0xB959 NR5G ML1 RLM Stats      0xB885 NR5G MAC DCI Info
0xB89B NR5G MAC UCI Information 0xB896 NR5G MAC UCI Payload Information
0xB860 NR5G PDCP UL Stats      0xB868 NR5G RLC UL Stats
0xB823 NR5G RRC Serving Cell Info 0xB821 NR5G RRC OTA Packet
0xB890 NR5G MAC CDRX Events Info
```

注意：log.txt 里没有 0xB975/B9A4/B9A5/BA03（Beam Management / BFR Ind / BFD Ind）——
它们是本 HDF 中未打开 mask 的消息（后经 QCAT 枚举确认），所以波束失败只能用
ML1 RLM Stats（Purpose=BEAM_FAILURE）和 MAC Skip UL TX 的 TX_SUSPEND 来推断。

## 2. 时间基准对齐（设备时钟 vs 用户时钟）

设备日志时间：2026-10-09 07:52:01–07:59:53（QCAT 读 HDF 头得到）。
PCAP 时间：2026-10-09 15:42–15:59（PC 本地时间，Asia/Shanghai，UTC+8）。
=> 设备时钟 = UTC（07:52 UTC = 15:52 CST，落在 pcap 捕获窗口内）。

用户叙述的事件时间 13:28:13–13:28:38 与日志事件通过**不变量**对齐：

| 用户描述 | 日志事实 | 换算 |
|---|---|---|
| 13:28:13 前 3–4 次波束失败，每次 RACH 恢复 | 07:57:58.8 / 07:58:04.3 / 07:58:04.4 / 07:58:09.4 / 07:58:10.2 的 BFR RACH，Attempt 均 SUCCESS | 07:58:xx + 5:30 = 13:28:xx |
| 13:28:13–35 无 BSR/SR/RACH | 07:58:15–07:58:36 DCI=0、SR/BSR 停止、无 RACH | 同上 |
| 13:28:38 在 PCI-460 恢复 | 07:58:38.83 语音 PDCP 恢复（重建后） | 同上 |

即：用户时间 = 设备时间 + 5:30（印度 IST，与日志 PLMN MCC=405 一致）。设备时钟就是 UTC。

## 3. 用 QCAT 自动化接口解码 HDF

机器上装有 `C:\Program Files (x86)\Qualcomm\QCAT 6.x`（版本 06.30.121）。
QCAT 提供 COM 自动化对象 `QCAT6.Application`，可以用 Strawberry Perl 的 Win32::OLE 调用。
先验证对象可用（qcat_test.pl）：

```perl
use Win32::OLE;
my $app = Win32::OLE->new('QCAT6.Application');
print $app->{AppVersion};   # 06.30.121
```

核心 API（来自 QCAT 自带的 Scripts 示例，如 FilteredIterationSample.pl / TimeWindowSample.pl）：

```perl
$app->{Visible} = 0;                 # 隐藏窗口
my $f = $app->{PacketFilter};        # 报文过滤器
$f->SetAll(0); $f->Set(0xB873, 1); … # 只保留关心的 log code
$f->Commit();
$app->OpenLog($hdf);                 # 打开 HDF
my $p = $app->{FirstPacket};         # 迭代
while ($p) { print $p->{Text}; $p->Next(); }
```

`qcat_list.pl` 用 `$app->{SupportedPackets}` 枚举 QCAT 支持的 NR5G 消息，
从中选出与上行调度/波束/RLF 相关的 26 个 log code 喂给 qcat_dump.pl：

```
BSR/UL:  0xB873,0xB870,0xB872,0xB880*,0xB8A0*,0xB871
调度:    0xB885(DCI),0xB89B(UCI),0xB896(UCI Payload),0xB883,0xB884*,0xB890(CDRX)
跳过:    0xB8AE(Skip UL TX)
RACH:    0xB889,0xB88A
RLM/波束: 0xB959,0xB975*,0xB9A4*,0xB9A5*,0xBA03*,0xB8A7(CSF),0xB8D8(SNR),0xB97F,0xB950,0xB981*
RRC/NAS: 0xB821(OTA),0xB822(MIB),0xB823(ServingCell),0xB825
缓冲:    0xB860(PDCP UL Stats),0xB868(RLC UL Stats),0xB89C(Flow Control)
（* 表示本 HDF 中无此类报文，未出结果）
```

qcat_dump.pl 的输出格式（按块）：

```

2026 Oct  9  07:53:58.128  [41]  0xB889  NR5G MAC RACH Trigger
Subscription ID = 1
...
Rach Reason = BEAM_FAILURE
```

运行结果：HDF 共 **12,094,907** 个原始包，过滤后命中 **82,832** 条，
写入 decoded.txt（约 397MB）。首轮未加波束消息时是 80,216 条（decoded_v1.txt）。

## 4. 解析 decoded.txt（表格式报文的通用解法）

parse_decoded.py 按 `=== idx <code> ===` 切块：

```python
def iter_blocks(path):
    cur = None
    with open(path, encoding='utf-8', errors='replace') as f:
        for line in f:
            m = re.match(r'=== (\d+)\t(0x[0-9A-F]+) ===', line)
            if m:
                if cur: yield cur
                cur = [int(m.group(1)), m.group(2), []]
            elif cur is not None:
                cur[2].append(line.rstrip('\n'))
        if cur: yield cur
```

QCAT 的表格式输出结构是：元数据行 → 表头（多行，列名被拆成几行） → 一条长虚线 → 数值行。
数值行的列位与表头末行的叶子列一一对应。因此通用的取值方法是：

```python
def value_rows(lines):
    last_dash = -1
    for i, ln in enumerate(lines):
        if re.match(r'^\s*-{20,}', ln):
            last_dash = i
    rows = []
    for ln in lines[last_dash+1:]:
        ln = ln.strip()
        if ln.startswith('|'):
            rows.append([f.strip() for f in ln.strip('|').split('|')])
    return rows
```

各消息的关键列位（与表头逐列对照得到）：

| 消息 | 关键字段（列号） |
|---|---|
| Skip UL TX | [5]=Drop Reason, [6]=Drop Chan Type |
| RLM Stats | 文本行 `Purpose = BEAM_FAILURE / RLF` |
| UCI Information | [9]=UCI Request Bitmask, [11]=Num SR, [23]=SR Request（无HARQ数据时） |
| DCI Info | [7]=DCI Format（UL_0_1 / DL_1_1 …） |
| L2 UL BSR | [6]=Trigger Reason, [8]=BSR Length, [9]=LCG Bitmask, [11..13]=LCID |
| PDCP UL Stats | [1]=RB ID, [6]=PDCP Count, [12]=Total RX Bytes, [13]=Current WM Bytes, [9]=Discard Packets |
| CDRX Events | [12]=Active Procedure（SR_ACTIVE 等） |
| RACH Trigger | 文本行 `Rach Reason = ...` |
| RACH Attempt | 文本行 `RACH Result = ...`, `SSB ID = ...` |
| RRC Serving Cell Info | 文本行 `Physical Cell ID = ...` |
| RRC OTA Packet | 首行 `-- UL_DCCH / MeasurementReport` 等 + `Physical Cell ID` |

## 6. PCAP 解析（pcap_info.py / pcap_flow.py / pcap_gap.py）

pcap 的链路层不是标准 Ethernet：前 14–24 字节是私有头。解析时不是死认偏移，
而是在前 64 字节内扫描 IPv4（0x45, proto=17/58）或 IPv6（version=6, next header=17/58）的起点：

```python
for cand in range(0, min(64, len(data)-20)):
    if data[cand] >> 4 == 6 and data[cand+6] in (17, 58): off = cand; break
    if data[cand] == 0x45 and data[cand+9] in (17, 58): off = cand; break
```

mo.pcap 的主 UDP 流：`2409:40f0:...:c82e:46620 -> 2406:da1a:...:baa1:449`（RTP，约 34 包/秒）。
按秒直方图可见：正常语音 → 中断（每秒只剩 1–5 个 88–768B 小包）→ 恢复，
中断/恢复形态与 UE 侧 RLF、重建一致。因 PCAP 时钟与设备时钟基准不同，
本分析只把它当作方向性佐证，未做逐包对齐。

## 8. 结论

1. BSR 实际**触发过**（LCG1），SR 也发出去 3 次，但 13:28:14.7 后网络不再下发任何 DCI，
   BSR/SR 没有可用的 PUSCH/PUCCH 机会。
2. PUCCH/PUSCH 之所以发不出去，是 MAC 在波束失败状态下主动跳过（Skip UL TX / TX_SUSPEND）。
3. 波束失败每秒都在发生（RLM BEAM_FAILURE），BFR RACH 在 13:28:36.7 后因 Msg3 的 PUSCH 同样被
   挂起（TX_RACH_ABORT）而连续 Msg4 超时 → RACH 中止 → RLF → RRC 重建到 PCI 460。
4. 因此根因是服务小区 347 波束级链路持续失效且网络侧未恢复波束/调度，UE 侧 MAC 上行挂起
   把 SR/BSR 全部压制；RRC 配置有效与否在此场景下不是决定因素。
